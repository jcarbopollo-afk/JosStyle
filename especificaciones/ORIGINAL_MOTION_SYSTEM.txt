JOS STYLE — MOTION SYSTEM
FASE 16 — ESTADOS DE SISTEMA, LOADING, ERROR, OFFLINE, SYNC Y TRANSICIONES ASÍNCRONAS
Esfuerzo recomendado: ULTRACODE
 
⸻
 
MISIÓN
Construir un sistema global de motion para todos los estados en los que Jos Style no tiene inmediatamente el resultado final disponible.
La aplicación debe gestionar visualmente:
* loading;
* skeleton;
* fetching;
* refreshing;
* optimistic UI;
* saving;
* saved;
* syncing;
* synced;
* offline;
* reconnecting;
* error;
* retry;
* partial data;
* stale data;
* empty;
* permission states;
* authentication states;
* delayed responses;
* cancelled operations;
* failed operations.
El objetivo:
El usuario nunca debe sentir que la aplicación se ha quedado congelada, ha perdido información o ha cambiado de estado arbitrariamente.
 
⸻
 
1. AUDITORÍA ASÍNCRONA
Analizar todo el proyecto y localizar:
* fetches;
* queries;
* mutations;
* Supabase;
* auth;
* loading states;
* skeletons;
* spinners;
* errors;
* retry;
* optimistic updates;
* realtime;
* sync;
* persistence;
* offline handling.
Crear un mapa real.
No asumir que todo utiliza el mismo patrón.
 
⸻
 
2. STATE MACHINE
Cuando sea necesario, modelar estados explícitos:
idle
→ loading
→ success
o:
idle
→ loading
→ error
→ retrying
→ success
o:
saved
→ saving
→ synced
Evitar booleanos contradictorios como:
isLoading = true
isError = true
isSaved = true
simultáneamente sin intención.
 
⸻
 
3. MOTION STATE OWNERSHIP
Cada estado asíncrono debe tener un responsable claro de su motion.
No permitir que:
* componente;
* hook;
* router;
* data layer;
compitan por animar el mismo elemento.
Integrar con:
Motion Orchestrator.
 
⸻
 
4. INITIAL LOADING
Auditar el arranque inicial.
Evitar:
blank screen
→ sudden content
cuando una transición mejor sea posible.
Pero tampoco crear una animación de entrada larga que retrase la utilización de la aplicación.
 
⸻
 
5. APP BOOT
Coordinar:
app boot
+
auth
+
data
+
layout
+
motion
El contenido debe aparecer cuando realmente esté preparado.
 
⸻
 
6. SKELETON SYSTEM
Unificar skeletons.
Definir:
* entrada;
* salida;
* shimmer;
* duración;
* intensidad;
* agrupación.
Evitar skeletons completamente diferentes entre módulos.
 
⸻
 
7. SKELETON EXIT
Cuando llega contenido real:
evitar:
skeleton disappears
content appears
como dos estados desconectados.
Usar una transición coherente.
 
⸻
 
8. SKELETON MORPH
Cuando sea viable:
permitir continuidad espacial entre:
skeleton
→
real content
especialmente en:
* cards;
* listas;
* dashboard;
* widgets.
 
⸻
 
9. SKELETON TIMEOUT
Si una petición tarda demasiado:
no mantener indefinidamente un shimmer sin información.
Determinar cuándo pasar a:
* delayed state;
* retry;
* error;
* partial state.
 
⸻
 
10. SPINNERS
Auditar todos los spinners.
No utilizar spinner por defecto para cualquier cosa.
Diferenciar:
* microacción;
* carga de pantalla;
* carga de sección;
* operación larga.
 
⸻
 
11. MICRO LOADING
Para operaciones muy rápidas:
evitar mostrar:
loading
→
success
si el estado dura tan poco que solo genera parpadeo.
Aplicar delay mínimo de aparición cuando corresponda.
 
⸻
 
12. LOADING HYSTERESIS
No mostrar y ocultar indicadores demasiado rápidamente.
El objetivo es evitar:
flash
visuales.
 
⸻
 
13. LONG OPERATIONS
Para operaciones largas:
mostrar progreso o estado contextual cuando sea posible.
No fingir progreso.
 
⸻
 
14. OPTIMISTIC UI
Auditar operaciones donde sea correcto actualizar primero la UI:
user action
→
visual change
→
server sync
La animación debe reflejar que el cambio es provisional cuando sea necesario.
 
⸻
 
15. OPTIMISTIC SUCCESS
Si el servidor confirma:
hacer transición natural:
optimistic
→
confirmed
sin rehacer visualmente todo el componente.
 
⸻
 
16. OPTIMISTIC ROLLBACK
Si falla:
optimistic
→
rollback
Debe existir una transición clara.
Evitar teletransportar el contenido a su estado anterior.
 
⸻
 
17. ERROR MOTION
Los errores deben comunicar:
algo ha fallado.
Sin convertirse en una animación molesta.
Usar:
* shake sutil;
* color/state transition;
* inline error;
* icon transition;
solo donde aporten significado.
 
⸻
 
18. ERROR RECOVERY
Al pulsar:
Retry
la transición debe ser:
error
→
retrying
→
success/error
Nunca:
error
→
everything disappears
sin motivo.
 
⸻
 
19. ERROR LOCAL
Un error de un componente no debe animar toda la página.
Ejemplo:
si falla una card:
card error
no:
entire dashboard error
 
⸻
 
20. PARTIAL FAILURE
Si 1 módulo falla y otros funcionan:
mantener disponibles los demás.
Motion debe respetar la independencia de módulos.
 
⸻
 
21. EMPTY VS ERROR
Diferenciar claramente:
empty
de:
error
y:
loading
Cada uno necesita una transición apropiada.
 
⸻
 
22. EMPTY → CONTENT
Cuando el usuario crea el primer elemento:
empty state
→
new content
hacer una transición de transformación contextual.
No simplemente reemplazar todo.
 
⸻
 
23. CONTENT → EMPTY
Si el usuario elimina el último elemento:
content
→
empty
animar la desaparición y después introducir el estado vacío.
 
⸻
 
24. DELETE + SERVER
Cuando se elimina:
user action
→
optimistic removal
→
server confirmation
Si falla:
rollback
respetando el contexto original.
 
⸻
 
25. UNDO
Si existe undo:
delete
→
undo available
→
restore
El elemento debe regresar a su posición contextual cuando sea posible.
 
⸻
 
26. SYNC STATE
Crear lenguaje visual consistente para:
local
→
syncing
→
synced
No abusar de indicadores permanentes.
 
⸻
 
27. SAVING
Para acciones de guardado:
evitar que un botón haga:
Guardar
→
spinner
→
Guardar
Preferir:
Guardar
→
Guardando
→
Guardado
cuando aporte valor.
 
⸻
 
28. SYNC MICROINTERACTION
El estado de sincronización debe ser:
* discreto;
* rápido;
* no invasivo.
No hacer que una aplicación personal parezca una consola de servidor.
 
⸻
 
29. OFFLINE
Si la app puede funcionar parcialmente offline:
definir:
online
offline
reconnecting
online
con motion mínimo.
 
⸻
 
30. OFFLINE ENTRY
Cuando se pierde conexión:
no lanzar una animación global exagerada.
Utilizar una señal contextual.
 
⸻
 
31. RECONNECTING
Mostrar estado de reconexión cuando sea útil.
Evitar loops infinitos de animación llamativos.
 
⸻
 
32. RECONNECTED
Cuando vuelve la conexión:
reconnecting
→
synced
con feedback corto.
 
⸻
 
33. OFFLINE ACTIONS
Si una acción puede ejecutarse offline:
representarla como:
local change
→
pending sync
No fingir que el servidor ya confirmó.
 
⸻
 
34. REALTIME DATA
Si existe Supabase Realtime u otro flujo realtime:
auditar cómo entra información externa.
No permitir que nuevos datos:
teleport
al layout.
 
⸻
 
35. REMOTE UPDATE
Cuando otro origen modifica datos:
usar:
* layout motion;
* content transition;
* counter transition;
* list insertion.
según el caso.
 
⸻
 
36. CONFLICTS
Si existe conflicto entre:
local state
y:
remote state
la transición debe comunicar el cambio sin destruir el contexto del usuario.
 
⸻
 
37. REFRESH
Diferenciar:
initial load
de:
refresh
Un refresh no debería borrar todo el contenido y volver a mostrar skeleton.
Preferir:
existing content
+
subtle refresh state
cuando sea correcto.
 
⸻
 
38. PULL TO REFRESH
Si existe:
integrar con:
* gesture physics;
* spring;
* loading;
* release;
* success/error.
No crear un sistema independiente.
 
⸻
 
39. NAVIGATION + ASYNC
Si el usuario navega mientras se carga algo:
evitar bloquear toda la app salvo que sea realmente necesario.
 
⸻
 
40. CANCELLATION
Si una operación se cancela:
la UI debe poder:
loading
→
cancelled
sin dejar spinners huérfanos.
 
⸻
 
41. RACE CONDITIONS
Probar:
request A
request B
response B
response A
La UI no debe volver al estado antiguo incorrectamente.
 
⸻
 
42. STALE DATA
Si existen datos antiguos mientras llegan datos nuevos:
no hacer:
old
→
blank
→
new
si puede hacerse:
old
→
updating
→
new
 
⸻
 
43. DATA TRANSITIONS
Integrar los cambios de datos con:
Layout Motion Engine
y:
Motion Orchestrator.
No duplicar lógica.
 
⸻
 
44. AUTH STATES
Auditar:
* login;
* logout;
* session restore;
* session expiration;
* authentication loading.
Evitar flashes de:
login
→
app
→
login
 
⸻
 
45. SESSION EXPIRATION
Si la sesión expira:
la transición debe ser contextual y clara.
No borrar la interfaz instantáneamente sin explicación.
 
⸻
 
46. PERMISSION STATES
Si un módulo depende de permisos:
diferenciar:
* checking;
* granted;
* denied;
* unavailable.
No mostrar error cuando simplemente todavía se está comprobando.
 
⸻
 
47. NOTIFICATIONS
Las notificaciones de estado deben respetar:
* prioridad;
* motion hierarchy;
* reduced motion;
* contexto.
 
⸻
 
48. ASYNC MOTION PRIORITY
Prioridad:
1. user action
2. critical state
3. navigation
4. data update
5. decorative
Nunca permitir que una animación decorativa bloquee una acción.
 
⸻
 
49. INTERRUPTIBLE ASYNC MOTION
Una operación visual debe poder ser interrumpida.
Ejemplo:
loading
→
user navigates
No esperar artificialmente a que termine una animación innecesaria.
 
⸻
 
50. UNMOUNT SAFETY
Cuando un componente desaparece:
limpiar:
* timers;
* RAF;
* subscriptions;
* animation callbacks;
* observers.
No permitir motion sobre elementos desmontados.
 
⸻
 
51. PERFORMANCE
No permitir que loading:
* shimmer;
* blur;
* skeleton;
* realtime;
* polling;
generen actividad excesiva.
Especialmente en móvil.
 
⸻
 
52. REDUCED MOTION
Todos los estados asíncronos deben respetar:
full motion
reduced motion
no motion
sin perder información semántica.
 
⸻
 
53. ACCESSIBILITY
El usuario debe poder comprender el estado sin depender del movimiento.
Motion comunica.
No sustituye:
* texto;
* labels;
* ARIA;
* estados semánticos.
 
⸻
 
54. IMPLEMENTACIÓN
Implementar realmente las mejoras.
No crear solamente:
MOTION_SYSTEM.md
Debe modificarse el código donde sea necesario.
 
⸻
 
55. NO REWRITE
No reescribir módulos completos si ya funcionan.
Integrar sobre la arquitectura existente.
Crear abstracciones nuevas únicamente cuando exista una necesidad real.
 
⸻
 
56. DOCUMENTACIÓN
Actualizar:
MOTION_SYSTEM.md
con:
* async state model;
* loading;
* skeleton;
* optimistic UI;
* rollback;
* error;
* offline;
* sync;
* realtime;
* cancellation;
* race conditions;
* accessibility.
 
⸻
 
57. QA
Ejecutar escenarios reales:
slow network
fast network
network failure
reconnect
server error
retry
cancel
rapid actions
navigation during load
delete + undo
optimistic rollback
session restore
 
⸻
 
58. VALIDACIÓN TÉCNICA
Ejecutar:
* build;
* lint;
* typecheck;
* tests;
* verificar.sh si existe.
Resolver todos los errores introducidos.
 
⸻
 
59. REGRESIÓN
Comprobar que las fases anteriores siguen funcionando:
* Motion Engine;
* Orchestrator;
* transitions;
* gestures;
* layout motion;
* responsive;
* accessibility;
* performance.
 
⸻
 
60. REGLA PERMANENTE
Toda nueva operación asíncrona de Jos Style debe definir:
idle
loading
success
error
y, cuando corresponda:
saving
syncing
offline
retrying
cancelled
rollback
El Motion System deve ser parte del flujo de estado, no una capa añadida después.
 
⸻
 
61. CONTINUACIÓN AUTOMÁTICA
Al terminar:
1. implementar;
2. auditar;
3. verificar;
4. corregir;
5. ejecutar tests;
6. documentar;
7. actualizar roadmap.
Después continuar automáticamente con:
FASE 17 — MOTION DE DATOS, DASHBOARD, MÉTRICAS, GRÁFICAS Y VISUALIZACIÓN DE INFORMACIÓN
No pedir confirmación.
Si durante la implementación descubres una dependencia necesaria:
impleméntala correctamente antes de continuar.
 
⸻
 
RESULTADO ESPERADO
Jos Style debe comportarse como una aplicación viva.
Cuando algo está cargando:
se entiende.
Cuando algo cambia:
se percibe.
Cuando algo falla:
se comunica.
Cuando algo se sincroniza:
se confirma.
Cuando algo desaparece:
se conserva el contexto.
Y cuando no hay nada que mostrar:
la interfaz lo expresa sin parecer rota.
Todo ello sin sacrificar:
rendimiento + accesibilidad + claridad + continuidad + elegancia.
Esfuerzo: ULTRACODE.


JOS STYLE — MOTION SYSTEM
FASE 17 — MOTION DE DATOS, DASHBOARD, MÉTRICAS, GRÁFICAS Y VISUALIZACIÓN DE INFORMACIÓN
Esfuerzo recomendado: ULTRACODE
 
⸻
 
MISIÓN
Construir un sistema global para que los datos de Jos Style aparezcan, cambien, desaparezcan y se comparen mediante movimiento coherente.
La aplicación debe conseguir que:
* números;
* métricas;
* estadísticas;
* gráficas;
* barras;
* anillos;
* porcentajes;
* rankings;
* listas;
* widgets;
* indicadores;
* tendencias;
* objetivos;
* progreso;
se sientan vivos, pero nunca artificialmente animados.
Principio fundamental:
El movimiento debe ayudar a comprender el dato, no distraer del dato.
 
⸻
 
1. AUDITORÍA GLOBAL DE DATOS
Localizar todos los lugares donde Jos Style representa información dinámica.
Buscar:
* counters;
* percentages;
* charts;
* progress bars;
* rings;
* sparklines;
* dashboards;
* cards;
* badges;
* streaks;
* statistics;
* goals;
* scores;
* rankings;
* summaries.
Crear un mapa de componentes.
 
⸻
 
2. DATA MOTION ENGINE
Determinar si el proyecto ya dispone de una abstracción para animar datos.
Si existe:
mejorarla.
Si no existe y realmente hace falta:
crear un sistema centralizado.
No crear animaciones independientes para cada métrica.
 
⸻
 
3. NUMERIC COUNTERS
Los números que cambian significativamente pueden utilizar transición.
Ejemplo:
72
→
74
Debe evitarse que el número simplemente aparezca de golpe cuando el cambio tenga importancia visual.
 
⸻
 
4. COUNTER INTELLIGENCE
No animar cualquier número.
Diferenciar:
critical metric
secondary metric
static number
timestamp
identifier
Un identificador nunca debería hacer una animación innecesaria.
 
⸻
 
5. VELOCIDAD DEL COUNTER
La duración debe depender del cambio de valor de forma razonable.
No permitir:
1
→
100000
con una animación interminable.
 
⸻
 
6. COUNTER INTERRUPTION
Si el valor cambia mientras el counter está animándose:
no reiniciar desde cero.
Continuar desde el valor visual actual hacia el nuevo objetivo.
 
⸻
 
7. COUNTER RAPID UPDATES
Si llegan múltiples actualizaciones:
agruparlas cuando sea apropiado.
Evitar:
10
11
12
13
14
15
como cinco animaciones consecutivas.
 
⸻
 
8. FORMAT PRESERVATION
Durante el counter:
mantener correctamente:
* decimales;
* unidades;
* porcentajes;
* monedas;
* separadores;
* prefijos;
* sufijos.
Nunca producir:
€1
€10
€100
cuando el formato real requiera otra representación.
 
⸻
 
9. NUMERIC ACCESSIBILITY
El valor semántico final debe ser accesible independientemente de la animación.
Screen readers no deben leer cada frame.
 
⸻
 
10. PROGRESS BARS
Auditar:
* width;
* transform;
* color/state;
* label;
* completion.
Preferir transform cuando sea posible para rendimiento.
 
⸻
 
11. PROGRESS CHANGES
Ejemplo:
42%
→
68%
La barra debe acompañar al valor.
No permitir:
number → 68
bar → 42
durante demasiado tiempo.
 
⸻
 
12. PROGRESS COMPLETION
Cuando se alcanza:
100%
usar un feedback breve si tiene sentido.
Nunca convertir cada 100% en una celebración exagerada.
 
⸻
 
13. GOALS
Para objetivos:
current
→
progress
→
goal
la visualización debe dejar clara la relación.
 
⸻
 
14. STREAKS
Las rachas pueden utilizar microinteracción al aumentar.
Ejemplo:
7
→
8
Debe ser rápida y discreta.
 
⸻
 
15. ACHIEVEMENT MOTION
Para hitos importantes:
usar una jerarquía superior.
Ejemplo:
normal update
< milestone
< major achievement
No todas las actualizaciones deben tener la misma intensidad.
 
⸻
 
16. DASHBOARD ENTRY
Cuando se carga el dashboard:
evitar que todas las cards entren simultáneamente con el mismo movimiento.
Crear:
* jerarquía;
* stagger;
* prioridad;
* agrupación.
 
⸻
 
17. DASHBOARD STAGGER
El stagger debe ser corto.
No hacer que el usuario espere a que aparezcan las últimas cards.
La aplicación debe sentirse rápida.
 
⸻
 
18. ABOVE-THE-FOLD PRIORITY
Priorizar:
1. contenido principal;
2. acciones principales;
3. métricas importantes;
4. contenido secundario;
5. decoración.
 
⸻
 
19. DASHBOARD REFRESH
Cuando se actualizan datos:
no rehacer toda la entrada del dashboard.
Actualizar únicamente lo que cambió.
 
⸻
 
20. WIDGET ISOLATION
Si un widget cambia:
solo él debería reaccionar cuando sea posible.
Ejemplo:
Sueño update
no debe provocar una animación de:
Entreno
Economía
Tareas
sin motivo.
 
⸻
 
21. CARD DATA TRANSITIONS
Cuando una card cambia:
mantener:
* posición;
* tamaño;
* jerarquía;
mientras cambia el contenido.
Integrar con Layout Motion.
 
⸻
 
22. GRAPH SYSTEM
Auditar las gráficas existentes.
Identificar:
* line charts;
* bar charts;
* area charts;
* pie/donut;
* progress rings;
* sparklines.
No asumir que todos deben animarse igual.
 
⸻
 
23. CHART ENTRY
Una gráfica puede entrar:
draw
o mediante:
fade
según el tipo.
Elegir el método que mejore comprensión.
 
⸻
 
24. LINE CHARTS
Si existe una gráfica de líneas:
la entrada puede utilizar una revelación progresiva.
Pero evitar animaciones demasiado largas.
 
⸻
 
25. BAR CHARTS
Las barras pueden crecer desde su base.
Respetar:
* orientación;
* escala;
* valores;
* baseline.
 
⸻
 
26. DONUT / PIE
No rotar indefinidamente.
Si se utiliza entrada animada:
hacerla breve y comprensible.
 
⸻
 
27. SPARKLINES
Las sparklines deben ser extremadamente discretas.
No convertirlas en pequeñas animaciones decorativas constantes.
 
⸻
 
28. CHART DATA UPDATE
Cuando cambian los datos:
no desmontar y montar toda la gráfica.
Intentar interpolar cuando sea correcto.
 
⸻
 
29. DATA INTERPOLATION
Para:
value A
→
value B
interpolar de manera controlada.
No interpolar datos cuando pueda generar una interpretación falsa.
 
⸻
 
30. IMPORTANT: NO FABRICAR DATOS
Nunca crear movimiento que haga parecer que existe información intermedia real si no existe.
Ejemplo:
si una métrica pasa:
20
→
80
el counter puede interpolar visualmente.
Pero una gráfica histórica no debe inventar puntos intermedios que sugieran mediciones reales.
 
⸻
 
31. GRAPH AXIS STABILITY
Evitar que el eje cambie violentamente durante cada actualización.
Si la escala cambia:
hacerlo de forma coherente.
 
⸻
 
32. GRAPH RESCALE
Cuando sea necesario cambiar:
max
min
axis
coordinar:
* data;
* axis;
* labels.
Evitar que cada parte se anime a una velocidad diferente.
 
⸻
 
33. LEGENDS
Cuando aparece/desaparece una serie:
la leyenda y la gráfica deben coordinarse.
 
⸻
 
34. FILTERED DATA
Si el usuario filtra:
all
→
selected
la transición debe comunicar qué datos desaparecen y cuáles permanecen.
 
⸻
 
35. DATE RANGE
Cambiar:
7 days
→
30 days
no debe provocar una gráfica completamente nueva sin contexto.
Mantener continuidad cuando sea técnicamente correcto.
 
⸻
 
36. TAB SWITCHING
Entre métricas o periodos:
usar transiciones cortas.
No utilizar navegación pesada.
 
⸻
 
37. TOOLTIP MOTION
Los tooltips de gráficas deben:
* seguir el punto;
* evitar flicker;
* aparecer rápidamente;
* desaparecer limpiamente.
 
⸻
 
38. TOUCH CHART INTERACTION
En móvil:
adaptar interacción a touch.
No depender de hover.
 
⸻
 
39. POINTER CHART INTERACTION
En desktop:
aprovechar:
* hover;
* pointer;
* precise cursor interaction.
sin hacer la experiencia dependiente exclusivamente de ello.
 
⸻
 
40. CROSSHAIR / ACTIVE POINT
Si existe:
animarlo con continuidad.
Evitar saltos al pasar entre puntos cercanos.
 
⸻
 
41. DATA SORTING
Cuando una lista se reordena:
utilizar Layout Motion / FLIP.
Ejemplo:
rank 4
→
rank 1
El elemento debe moverse desde su posición anterior.
 
⸻
 
42. RANKING CHANGES
En rankings:
mantener identidad del elemento.
Nunca hacer:
remove all
→
recreate all
si puede evitarse.
 
⸻
 
43. FILTERED LISTS
Al filtrar:

Cada interacción importante del usuario debe producir una respuesta visual clara, rápida y elegante.

El objetivo NO es que todo se mueva.

El objetivo es que:

cada acción tenga exactamente el movimiento que necesita.

Jos Style debe sentirse:

* inmediato
* táctil
* preciso
* refinado
* vivo
* premium

1. AUDITORÍA DE COMPONENTES

* iconos
* cards

* radios
* sliders

* tooltips

* controles de gráficos

* acciones destructivas
* acciones de confirmación

No asumas que todos existen.

Cada interacción debe responder en el momento correcto.

No:

usuario toca
↓
espera
↓
animación.

Preferir:

usuario toca
↓
feedback inmediato
↓
resultado.

La sensación de latencia debe ser mínima.

3. BUTTON MOTION

Analiza todos los botones.

Estados:

idle
hover
focus
pressed
disabled
loading
success
error

Implementar solo los estados relevantes para cada botón.

⸻

4. PRESS FEEDBACK

El botón debe responder al contacto.

Considerar:

* scale sutil
* desplazamiento mínimo
* cambio de elevación
* opacity
* background
* shadow

NO exagerar.

Un botón premium debe sentirse físicamente presionable.

⸻

5. RELEASE

Al soltar:

No volver simplemente al estado original.

El retorno debe sentirse natural.

Si corresponde:

spring muy ligero.

Evitar rebotes excesivos.

⸻

6. HOVER

En desktop:

analiza:

* elevación
* scale
* background
* border
* shadow
* icon movement

Pero no usar todas simultáneamente.

Elige según el componente.

En móvil:

hover NO debe ser requisito.

⸻

7. FOCUS

Especial atención a accesibilidad.

El focus debe:

* ser visible
* no molestar
* integrarse visualmente
* no desaparecer simplemente por estética

Animarlo solo si mejora la comprensión.

⸻

8. LOADING BUTTON

Cuando una acción tarda:

No permitir que el botón simplemente desaparezca.

Diseñar:

normal
→ loading
→ success/error

El contenido puede transformarse.

Ejemplo conceptual:

“Guardar”
→ indicador
→ “Guardado”

La transición debe conservar la identidad del botón.

⸻

9. SUCCESS

Las confirmaciones importantes deben tener feedback.

Pero:

NO utilizar confeti constantemente.

El éxito cotidiano debe ser sutil.

El éxito importante puede utilizar una animación más expresiva.

⸻

10. ERROR

El error debe comunicarse rápidamente.

Utilizar cuando corresponda:

* shake muy pequeño
* cambio de estado
* icon transition
* highlight

No crear animaciones agresivas.

Nunca hacer que un error parezca una celebración.

⸻

11. CARDS

Las cards son elementos fundamentales de Jos Style.

Analiza:

idle
hover
press
selected
expanded
collapsed
loading
success
error
disabled

⸻

12. CARD PRESS

Cuando el usuario pulsa una card:

debe existir feedback inmediato.

La card puede:

* reducir ligeramente escala
* cambiar elevación
* modificar sombra
* responder a posición

No usar transformaciones grandes.

⸻

13. CARD HOVER

En desktop:

la card puede elevarse ligeramente.

Pero evita que todas las cards de una pantalla parezcan estar flotando simultáneamente.

⸻

14. CARD EXPANSION

Cuando una card se expande:

no simplemente mostrar contenido.

El contenido debe aparecer progresivamente.

La expansión debe mantener:

* continuidad
* jerarquía
* espacio
* border radius
* sombra

⸻

15. CARD COLLAPSE

La salida debe ser tan cuidada como la entrada.

Nunca:

contenido desaparece
→ card salta.

El layout debe reorganizarse suavemente.

⸻

16. LISTAS

Cuando aparezcan elementos:

usar stagger cuando aporte valor.

Pero limitarlo.

Una lista de 30 elementos NO necesita 30 animaciones individuales.

Define estrategias para:

* listas cortas
* listas medias
* listas largas

⸻

17. ADD ITEM

Cuando el usuario añade:

* tarea
* hábito
* entrenamiento
* gasto
* registro
* elemento

el nuevo elemento debe aparecer con feedback.

No hacer que toda la lista se reconstruya visualmente.

⸻

18. REMOVE ITEM

Cuando se elimina:

primero comunicar la acción
→ después retirar el elemento.

El resto de la lista debe ocupar su espacio naturalmente.

⸻

19. UNDO

Si Jos Style tiene undo:

La desaparición y recuperación deben estar conectadas visualmente.

Ejemplo:

item sale
→ snackbar aparece
→ undo
→ item regresa.

No crear dos animaciones independientes.

⸻

20. TOGGLES

Los switches deben tener sensación física.

Considerar:

* thumb movement
* track
* color
* spring
* press feedback

El thumb debe desplazarse con continuidad.

⸻

21. CHECKBOXES

Estados:

unchecked
→ checked

checked
→ unchecked

Debe existir una transición clara.

Si corresponde:

icon check
→ draw/reveal.

No hacer una animación lenta para una acción que se realiza cientos de veces.

⸻

22. RADIO BUTTONS

Animar:

outer state
inner state

de forma rápida y precisa.

⸻

23. SLIDERS

Los sliders deben responder al dedo.

Cuando el usuario arrastre:

el valor debe actualizarse inmediatamente.

Si existe tooltip/valor flotante:

seguir el thumb.

No animar el valor con retraso perceptible.

⸻

24. TABS

Al cambiar de tab:

* indicador
* contenido
* estado seleccionado

deben estar coordinados.

No hacer:

indicador cambia
→ espera
→ contenido cambia.

Todo debe sentirse como una única acción.

⸻

25. DROPDOWNS

El menú debe parecer conectado al elemento que lo abrió.

Considerar:

* origen
* posición
* scale
* opacity
* shadow
* backdrop si existe

No aparecer desde el centro de la pantalla.

⸻

26. TOOLTIPS

Los tooltips deben evitar aparecer inmediatamente en acciones accidentales.

Utilizar un delay razonable.

La salida debe ser rápida.

No bloquear la interacción.

⸻

27. ICON BUTTONS

Botones de icono:

* press
* hover
* focus
* active

El icono puede tener una microrespuesta.

Pero evitar:

rotaciones aleatorias
rebotes
escalados excesivos.

⸻

28. DESTRUCTIVE ACTIONS

Eliminar datos importantes requiere claridad.

No utilizar una animación divertida.

Priorizar:

* confirmación

* continuidad

La animación debe reforzar que la acción es irreversible cuando corresponda.

* velocidad
* dirección
* aceleración
* distancia
* presión cuando esté disponible
* contexto
* estado actual

3. TOUCH RESPONSE

→ release
→ recover

5. SPRINGS

* masa
* damping
* stiffness

Crear familias:

soft
responsive
heavy
snappy

6. SPRING INTELLIGENCE

El mismo spring NO debe utilizarse para:

* un botón
* un bottom sheet
* una card
* una navegación
* un objeto arrastrable

7. DRAG

follow.

release.

8. DRAG OFFSET

No obligar al elemento a saltar para colocar su centro exactamente bajo el dedo.

→ vuelve.

drag rápido
→ dismiss.

No depender únicamente de distancia.

10. VELOCITY THRESHOLD

* minimum velocity
* dismiss velocity
* maximum velocity

⸻

+
velocidad
+
dirección

o
cancel.

threshold

Crear una abstracción reutilizable para shared elements.
Debe permitir definir conceptualmente:
sharedId
o equivalente.
El sistema debe poder reconocer:
origen
↓
elemento compartido
↓
destino
y crear una transición continua.
No implementar shared elements manualmente en cada pantalla.
 
⸻
 
5. CARD → DETAIL
Auditar todas las cards clicables.
Determinar cuáles merecen continuidad.
Prioridad:
1. elemento visual principal;
2. título;
3. icono;
4. superficie;
5. información secundaria.
No convertir cada card en una animación compleja.
La transición debe parecer natural.
 
⸻
 
6. DETAIL → BACK
Cuando el usuario vuelve:
el sistema debe intentar reconstruir:
DETAIL
↓
CARD ORIGINAL
La card debe reaparecer en su posición/contexto correspondiente.
Evitar:
detail
→ fade
→ dashboard
cuando existe una relación directa.
 
⸻
 
7. PRESERVACIÓN DEL CONTEXTO
Al navegar hacia otra vista:
preservar cuando sea posible:
* scroll position;
* estado de tabs;
* filtros;
* selección;
* expansión;
* posición visual.
La animación no debe ocultar una mala gestión del estado.
 
⸻
 
8. SCROLL POSITION + MOTION
Auditar qué ocurre cuando:
usuario hace scroll
→
abre detalle
→
vuelve
La aplicación debe decidir correctamente si:
* restaura scroll;
* mantiene contexto;
* reconstruye transición;
* evita un salto visual.
No permitir:
volver
↓
pantalla arriba
↓
scroll vuelve abajo
de forma visible y brusca.
 
⸻
 
9. TAB TRANSITIONS
Las tabs no deben comportarse como páginas completamente independientes.
Analizar:
* dirección del cambio;
* posición relativa de las tabs;
* contenido;
* indicador;
* estado anterior.
El indicador puede proporcionar continuidad espacial.
Ejemplo:
TAB A
   ↓

   ↓
TAB B
No simplemente:

10. BOTTOM NAVIGATION
La navegación inferior debe tener comportamiento consistente.
Auditar:
* iconos;
* labels;
* indicador activo;
* contenido;
* transición entre secciones.
Evitar que cada cambio de sección parezca una recarga completa.
El usuario debe percibir:
sigo dentro de Jos Style, simplemente estoy cambiando de espacio.

11. INDICADORES ACTIVOS
Los elementos activos deben cambiar de estado mediante motion.
Ejemplos:
* bottom navigation;
* tabs;
* filtros;
* segmented controls;
* switches.
El movimiento debe mostrar claramente:
previous state
→
new state
No utilizar simplemente:
opacity: 0
opacity: 1
si existe una oportunidad clara de continuidad.

12. PAGE TRANSITIONS

LEVEL 1 — MICRO

LEVEL 2 — CONTEXTUAL
Para cambio de sección:

LEVEL 3 — STRUCTURAL
Para:

→

LEVEL 4 — OVERLAY
Para:

13. DIRECCIÓN DEL MOVIMIENTO
No imponer una dirección global.
Determinar la dirección según la relación.
Ejemplo:
parent → child
puede acercarse.
child → parent
puede retirarse.
sibling → sibling
puede desplazarse lateralmente o utilizar transición mínima.
La dirección debe tener significado.
 
⸻
 
14. GESTURE CONTINUITY
Si la aplicación soporta:
* swipe;
* drag;
* dismiss gesture;
* sheet drag;
la animación debe responder al gesto de forma proporcional.
No:

→
soltar
→

Preferir:
gesture progress
→
animation progress
 
⸻
 
15. INTERACTIVE DISMISS
Para sheets/modals dismissibles:
el usuario debe poder percibir que controla físicamente el elemento.
Mientras arrastra:
* posición responde;
* backdrop responde;
* profundidad puede cambiar;
* contenido subyacente puede recuperar prioridad.
Al soltar:
threshold alcanzado
→ dismiss
o:
threshold no alcanzado
→ spring back
 
⸻
 
16. INTERRUPCIÓN DE ANIMACIONES
Las animaciones deben poder interrumpirse correctamente.
Ejemplo:
abrir
→
usuario pulsa cerrar inmediatamente
No esperar necesariamente a que termine la animación anterior.
Resolver correctamente:
current state
+
current progress
+
new target
Evitar:
* acumulación de animaciones;
* dobles callbacks;
* estados imposibles;
* flickering.

17. RAPID INTERACTION
Probar:
tap
tap
tap
tap
y:
open
close
open
close

No permitir:

* overlays duplicados;
* estados incorrectos;

↓

No convertir esto en una secuencia lenta.
Las fases deben solaparse cuando sea natural.
 
⸻
 
26. NO TELEPORTING
Auditar cualquier elemento que:
desaparece
↓
aparece en otro lugar

Eliminar “teleporting” visual siempre que sea razonable.

27. PRESENCIA DEL ESTADO ANTERIOR
Durante una transición, decidir qué parte del estado anterior debe permanecer visible.
No ocultar toda la pantalla demasiado pronto.
El contexto anterior puede servir como referencia espacial.
 
⸻
 
28. PRESENCIA DEL ESTADO NUEVO
El destino tampoco debe revelarse demasiado pronto si todavía no está preparado.
Evitar:

↓
layout cambia
↓

30. RESPONSIVE SHARED ELEMENTS
Shared transitions deben adaptarse a:
* móvil;

→

Recalcular correctamente.

Nunca dejar:

JOS STYLE — MOTION SYSTEM
FASE 8 — FÍSICA, SPRINGS, GESTOS E INTERACCIÓN DIRECTA
Esfuerzo recomendado: ULTRACODE
 
⸻
 
MISIÓN
Construir la capa de física e interacción directa de Jos Style.
Hasta ahora se han establecido:
* tokens de movimiento;
* profundidad;
* jerarquía visual;
* continuidad espacial;
* shared elements;
* navegación;
* transiciones.
Ahora el objetivo es conseguir que la interfaz responda como un sistema físico coherente.
Un elemento no debe simplemente:
reproducir una animación.
Debe:
responder a la acción del usuario.
La sensación buscada es:
rápida + precisa + natural + premium + controlable.
No queremos una interfaz “elástica” por defecto.
 
⸻
 
1. AUDITORÍA DE FÍSICA ACTUAL
Analiza todo el proyecto y localiza:
* springs;
* cubic-bezier;
* easing;
* drag;
* gestures;
* animations;
* transitions;
* momentum;
* inertia;
* snapping;
* overshoot;
* bounce;
* interactive transforms.
Determina qué sistema existe actualmente.
No introducir una segunda librería de física si la actual puede cubrir correctamente las necesidades.
 
⸻
 
2. PRINCIPIO DE FÍSICA
Definir reglas globales.
Una interacción física debe responder a:
input
↓
posición
↓
velocidad
↓
resistencia
↓
estado final
No utilizar springs simplemente porque “se sienten premium”.
Cada spring debe tener un propósito.
 
⸻
 
3. SPRING TOKENS
Crear tokens reutilizables para diferentes comportamientos.
Como mínimo estudiar:
SNAPPY
Para:
* toggles;
* botones;
* pequeños indicadores;
* cambios rápidos.
STANDARD
Para:
* cards;
* paneles;
* elementos generales.
SOFT
Para:
* sheets;
* superficies grandes;
* movimientos amplios.
RESPONSIVE
Para:
* elementos ligados directamente al dedo;
* drag;
* gestures.
Los parámetros reales deben adaptarse al motor utilizado.
No copiar valores genéricos sin probarlos.
 
⸻
 
4. NO TODO DEBE SER SPRING
Regla importante:
No reemplazar todas las transiciones por springs.
Utilizar:
timing
cuando:
* el movimiento es puramente visual;
* no existe interacción física;
* se necesita duración predecible.
Utilizar:
spring
cuando:
* existe interacción directa;
* hay retorno;
* hay desplazamiento físico;
* existe sensación de masa/inercia.
 
⸻
 
5. MASS
Analizar la sensación de masa.
Un elemento pequeño:
→ responde rápidamente.
Un elemento grande:
→ puede sentirse ligeramente más pesado.
Pero evitar que esto produzca una interfaz lenta.
La masa debe percibirse de forma sutil.
 
⸻
 
6. STIFFNESS
La rigidez determina cuánto intenta recuperar su posición.
Utilizar mayor rigidez para:
* controles;
* indicadores;
* microinteracciones.
Menor rigidez para:
* sheets;
* elementos grandes;
* movimientos físicos amplios.
No crear decenas de configuraciones.
Mantener una jerarquía pequeña.
 
⸻
 
7. DAMPING
El damping debe impedir rebotes excesivos.
Jos Style NO debe sentirse como:
* goma;
* gelatina;
* juguete;
* interfaz arcade.
La mayoría de los movimientos deben asentarse rápidamente.
 
⸻
 
8. OVERSHOOT
Auditar todos los overshoots.
Un pequeño overshoot puede aportar naturalidad.
Demasiado:
posición
→
se pasa
→
vuelve
→
se pasa
→
vuelve
es visualmente barato.
Eliminar oscilaciones innecesarias.
 
⸻
 
9. VELOCITY
La velocidad del gesto debe influir cuando tenga sentido.
Ejemplo:
un swipe rápido puede producir una salida más rápida que un drag lento.
No utilizar simplemente:
gesture detected
→
same animation
para todos los casos.
 
⸻
 
10. GESTURE PROGRESS
Cuando un elemento está ligado al gesto:
gesture 0%
→
element 0%
gesture 50%
→
element 50%
gesture 100%
→
element 100%
La respuesta debe ser perceptiblemente directa.
Evitar retraso entre dedo y elemento.
 
⸻
 
11. TOUCH FOLLOWING
Auditar elementos que siguen el dedo.
Especialmente:
* sheets;
* drawers;
* sliders;
* drag handles;
* cards dismissibles.
El movimiento debe sentirse conectado al input.
No debe parecer que el elemento persigue al dedo.
 
⸻
 
12. DRAG RESISTANCE
Cuando el usuario intenta arrastrar más allá del límite:
introducir resistencia.
Conceptualmente:
drag normal
→
1:1

drag beyond boundary
→
resistance
Esto comunica:
has llegado al límite.
No bloquear bruscamente el movimiento.
 
⸻
 
13. RUBBER-BANDING
Si se utiliza rubber-banding:
debe ser extremadamente sutil.
No permitir:
* deformaciones exageradas;
* movimientos absurdos;
* sensación de goma.
El objetivo es comunicar límites, no entretener.
 
⸻
 
14. SNAP POINTS
Para elementos con posiciones discretas:
definir puntos de snap.
Ejemplos:
sheet
→
collapsed
→
expanded
bottom panel
→
half
→
full
El sistema debe elegir el destino según:
* posición;
* velocidad;
* dirección;
* threshold.
 
⸻
 
15. VELOCITY-AWARE DISMISS
Un elemento puede cerrarse aunque no haya alcanzado el threshold si la velocidad del gesto indica claramente intención.
Ejemplo:
drag corto + velocidad alta
→ dismiss
Pero:
drag corto + velocidad baja
→ spring back
Ajustar con pruebas reales.
 
⸻
 
16. SHEET PHYSICS
Auditar todos los bottom sheets.
Deben responder a:
* drag;
* velocidad;
* resistencia;
* snap;
* dismiss.
Durante el gesto:
sheet position
+
backdrop opacity
+
underlying content
pueden responder conjuntamente.
 
⸻
 
17. MODAL INTERACTION
Los modales normalmente no deben ser excesivamente físicos.
Si permiten:
* dismiss;
* drag;
* swipe;
la física debe ser limitada.
No convertir un modal estándar en un juguete.
 
⸻
 
18. SLIDERS
Auditar:
* sliders;
* progress controls;
* range controls.
El thumb debe seguir directamente al dedo.
El valor debe actualizarse de forma estable.
Evitar:
finger
→
delay
→
thumb
 
⸻
 
19. TOGGLES
Los toggles deben tener una microfísica muy rápida.
Analizar:
* thumb;
* track;
* color;
* icon;
* label.
La sensación debe ser:
tap
→
response
→
settle
sin rebote exagerado.
 
⸻
 
20. BUTTON PRESS
Crear una respuesta de presión coherente.
Puede utilizarse:
* scale mínima;
* translate mínimo;
* opacity;
* highlight.
No combinar todo siempre.
El usuario debe percibir:
he pulsado algo.
No:
el botón ha hecho una animación.
 
⸻
 
21. CARD PRESS
Las cards interactivas pueden tener una respuesta ligeramente distinta.
Debe diferenciarse de un botón.
Analizar:
press
→
micro compression
→
release
No modificar el layout.
 
⸻
 
22. HAPTIC-READY ARCHITECTURE
Si el entorno permite feedback háptico:
crear puntos de integración semánticos.
Ejemplos:
selection
success
warning
dismiss
snap
No acoplar la lógica de movimiento directamente a una API específica si no es necesario.
 
⸻
 
23. POINTER VS TOUCH
Diferenciar cuando sea relevante:
* mouse;
* trackpad;
* touch;
* stylus.
Un hover puede existir en desktop.
No debe existir artificialmente en touch.
 
⸻
 
24. HOVER PHYSICS
Los hover deben ser extremadamente pequeños.
Evitar:
* cards flotando demasiado;
* movimientos exagerados;
* transformaciones constantes.
Un hover premium muchas veces es apenas perceptible.
 
⸻
 
25. CURSOR INTERACTION
Si existen elementos que reaccionan al cursor:
analizar:
* proximity;
* hover;
* pointer movement.
No implementar efectos de cursor por moda.
Solo si mejoran realmente la interfaz.
 
⸻
 
26. MAGNETIC EFFECTS
Si existen o se consideran efectos magnéticos:
auditar críticamente.
No aplicar a todos los botones.
Un efecto magnético debe:
* tener propósito;
* ser pequeño;
* responder rápidamente;
* no interferir con accesibilidad.
Si no aporta valor:
no implementarlo.
 
⸻
 
27. PARALLAX
Auditar cualquier parallax.
Debe ser:
* sutil;
* limitado;
* opcional;
* performant.
No utilizar parallax en contenido funcional importante.
 
⸻
 
28. SCROLL PHYSICS
Analizar interacción entre scroll y motion.
Especialmente:
* headers;
* sticky elements;
* floating buttons;
* cards;
* progress;
* collapsing sections.
Evitar que el scroll active animaciones innecesarias.
 
⸻
 
29. SCROLL-LINKED MOTION
Si se utilizan animaciones vinculadas al scroll:
preferir mecanismos performantes.
Evitar ejecutar lógica React pesada en cada frame si puede evitarse.
Auditar:
* requestAnimationFrame;
* browser-native scroll timelines cuando sean apropiadas;
* transforms;
* opacity.

* consciente del dispositivo;

1. AUDITORÍA DE ACCESIBILIDAD ACTUAL

2. PRINCIPIO FUNDAMENTAL
Separar:
MOTION
de:
MEANING
Si se elimina una animación:
el significado de la interacción debe permanecer.
Ejemplo:
animated check
puede convertirse en:
static check + state change

3. REDUCED MOTION GLOBAL
Implementar o perfeccionar una política global.
Debe existir una única fuente de verdad.
Evitar que cada componente implemente:

de manera independiente y diferente.

4. MOTION INTENSITY
Crear si resulta apropiado un concepto semántico de intensidad:

reduced
minimal
none
No necesariamente debe exponerse al usuario.
Puede utilizarse internamente para adaptar motion.
 
⸻
 
5. FULL MOTION
Con motion normal:
permitir la experiencia completa:
* springs;
* shared elements;
* transitions;
* depth;
* stagger;
* gestures;
* layout motion;
* microinteractions.
Siempre respetando los límites de rendimiento.
 
⸻
 
6. REDUCED MOTION
Con reduced motion:
reducir especialmente:
* grandes desplazamientos;
* zooms;
* parallax;
* rotaciones;
* movimientos continuos;
* stagger excesivo;
* cambios espaciales intensos.
Mantener cuando aporte información:
* fade corto;
* cambios de estado;
* focus;
* selección;
* feedback.
 
⸻
 
7. NO MOTION
Si se requiere una experiencia prácticamente estática:
la aplicación debe seguir siendo completamente funcional.
No:
animation disabled
→
component broken
 
⸻
 
8. REDUCED MOTION + GESTURES
Un gesto no debe desaparecer si también cumple una función funcional.
Ejemplo:
drag sheet
puede seguir funcionando aunque se reduzcan efectos decorativos.
Separar:
interaction
de:
decorative motion
 
⸻
 
9. REDUCED MOTION + NAVIGATION
La navegación debe seguir comunicando:
where you are
aunque se eliminen grandes transiciones.
Utilizar:
* cambio de contenido;
* focus;
* fade mínimo;
* cambios de estado.
 
⸻
 
10. REDUCED MOTION + SHARED ELEMENTS
Un shared element no debe provocar desplazamientos intensos cuando reduced motion está activo.
Utilizar una alternativa:
shared morph
→
simple crossfade
cuando corresponda.
 
⸻
 
11. REDUCED MOTION + LAYOUT
Las listas y layouts deben seguir actualizándose correctamente.
Reducir:
* spring;
* bounce;
* stagger.
Mantener:
* estabilidad;
* orden;
* claridad.
 
⸻
 
12. REDUCED MOTION + MICROINTERACTIONS
Botones, toggles, inputs y controles deben seguir proporcionando feedback.
Por ejemplo:

→
state change
en lugar de:

⸻
 
13. REDUCED MOTION + LOADING
Evitar loaders excesivamente animados.
Si existe reduced motion:
preferir:
* progress estático;
* skeleton simplificado;
* spinner reducido;
* estado textual cuando sea apropiado.
 
⸻
 
14. INFINITE MOTION

Buscar:
* spinners;
* pulses;
* shimmer;
* floating effects;
* background animation;
* decorative loops;
* notifications;
* breathing effects.

* alertas;
* notificaciones;

* contadores;

Una interfaz premium debe saber cuándo no moverse.

IMPORTANTE:
Esta fase NO consiste en eliminar animaciones para ganar rendimiento.
El objetivo es:
mantener la máxima calidad visual utilizando el mínimo coste técnico necesario.
 
⸻

* blur;

* transforms;

No optimices a ciegas.

2. PERFORMANCE BASELINE

* FPS;
* frame time;
* scripting;
* rendering;
* painting;
* layout;
* memory;
* input latency.
Identificar las pantallas más costosas.

3. FRAME BUDGET
Trabajar con el presupuesto de frame adecuado al dispositivo.
Como referencia:
60 Hz  ≈ 16.67 ms/frame
120 Hz ≈ 8.33 ms/frame
No asumir que conseguir 60 FPS significa que todo está perfectamente optimizado en una pantalla de 120 Hz.
 
⸻
 
4. FRAME DROPS
Identificar:
* jank;
* dropped frames;
* long tasks;
* stutters;
* freezes;
* animation hitching.
Localizar la causa antes de cambiar código.
 
⸻
 
5. MAIN THREAD
Reducir trabajo innecesario en el main thread durante animaciones.
Especialmente:
* cálculos;
* serialización;
* filtrado;
* sorting;
* renderizados masivos;
* mediciones DOM;
* estados React excesivos.
 
⸻
 
6. LAYOUT THRASHING
Buscar patrones:
READ
WRITE
READ
WRITE
READ
WRITE
dentro del mismo frame.
Agrupar lecturas y escrituras cuando corresponda.
 
⸻
 
7. FORCED SYNCHRONOUS LAYOUT

* offsetWidth;
* offsetHeight;
* getBoundingClientRect;
* scrollTop;
* scrollHeight;
* clientWidth;
* clientHeight.
Especialmente cuando aparecen inmediatamente después de modificar estilos.
 
⸻
 
8. FLIP
Donde Layout Motion necesite medir cambios:
usar correctamente estrategias tipo:
First
Last
Invert
Play
Evitar cálculos innecesarios.
 
⸻
 
9. TRANSFORM
Priorizar:
transform
para movimiento espacial cuando sea apropiado.
Evitar convertir todo indiscriminadamente a transforms.
La semántica y el layout real siguen siendo prioritarios.
 
⸻
 
10. OPACITY
Usar opacity cuando sea adecuado para:
* fades;
* crossfades;
* presence;
* overlays.
Evitar combinar opacity con demasiados efectos caros.
 
⸻
 
11. WIDTH / HEIGHT
Auditar animaciones de:
width
height
max-height
top
left
margin
padding

Cuando exista una alternativa estable:
considerar transform, clip, grid, layout animation u otras técnicas apropiadas.
 
⸻
 
12. AUTO HEIGHT
Los elementos dinámicos con:
height: auto
deben tener una estrategia de motion eficiente.
Especialmente:
* accordions;
* cards;
* sheets;
* contenido expandible.
Evitar medir continuamente durante toda la animación si no es necesario.
 
⸻
 
13. BLUR
Auditar:
filter: blur()
backdrop-filter: blur()
Son efectos potencialmente costosos.
Determinar dónde aportan valor real.
No eliminarlos automáticamente.
Optimizar:
* área afectada;
* duración;
* cantidad simultánea;
* frecuencia.
 
⸻
 
14. BACKDROP FILTER
Los elementos con:
backdrop-filter
deben revisarse especialmente en:
* overlays;
* navigation;
* sheets;
* modals;
* floating bars.
Evitar grandes áreas transparentes con blur innecesario.
 
⸻
 
15. SHADOWS
Auditar sombras animadas.
Especialmente:
box-shadow
durante movimiento continuo.
Cuando sea visualmente equivalente:
considerar alternativas más eficientes.
 
⸻
 
16. BORDER RADIUS
Revisar animaciones de:
border-radius
especialmente en shared elements.
Optimizar sin perder el morphing visual cuando realmente sea importante.
 
⸻
 
17. FILTER STACKS
Evitar combinar innecesariamente:

+
brightness
+
saturation
+
opacity
+

en grandes áreas.
 
⸻
 
18. COMPOSITING
Auditar qué elementos se convierten en capas independientes.
No utilizar will-change indiscriminadamente.
Una capa no es gratis.
 
⸻
 
19. WILL-CHANGE
Buscar:
will-change: transform;
permanente en componentes que no se animan continuamente.
Eliminar usos innecesarios.
Utilizarlo únicamente cuando aporte beneficio real.
 
⸻
 
20. GPU PROMOTION
No forzar GPU promotion en todos los elementos.
Medir primero.
La GPU no convierte automáticamente una animación en eficiente.
 
⸻
 
21. MEMORY
Auditar:
* animation objects;
* event listeners;
* cached measurements;
* DOM references;
* timelines;
* gesture state;
* shared element references.
Evitar referencias persistentes a componentes desmontados.
 
⸻
 
22. CLEANUP
Toda animación debe tener un ciclo de vida claro:
create
→ start
→ update
→ complete/cancel
→ cleanup
Ninguna animación debe quedar viva después de desaparecer su componente.
 
⸻
 
23. RAF MANAGEMENT
Centralizar requestAnimationFrame cuando sea apropiado.
Evitar decenas de loops independientes haciendo:
requestAnimationFrame
continuamente.
 
⸻
 
24. RAF CANCELLATION
Todo RAF debe poder cancelarse.
Especialmente al:
* unmount;
* route change;
* cancel;
* reduced motion;
* component disable.
 
⸻
 
25. SCROLL PERFORMANCE
Auditar scroll.
Evitar listeners pesados en:
scroll
Preferir mecanismos eficientes como:
* passive listeners;
* requestAnimationFrame;
* IntersectionObserver;
* CSS cuando sea suficiente.
 
⸻
 
26. SCROLL-LINKED MOTION
El movimiento dependiente del scroll debe:
* seguir el scroll;
* no bloquearlo;
* no producir jank;
* no ejecutar cálculos innecesarios.
 
⸻
 
27. POINTER PERFORMANCE
Auditar:
pointermove

touchmove

⸻
 
28. GESTURE PERFORMANCE
Los gestos deben tener:

* actualización visual fluida;
* mínima lógica durante movimiento;
* commit de estado al finalizar cuando sea apropiado.
 
⸻
 
29. STATE UPDATES
Buscar componentes que actualicen React state a altísima frecuencia durante una animación.

usar refs, valores animados u otras estrategias apropiadas.
No convertir cada frame en un render React.

* context updates;

Optimizar únicamente donde las mediciones lo justifiquen.

35. IMPORTS

Optimizar cuando sea posible.

38. CONTENT DENSITY

No aplicar el mismo presupuesto a:

39. VIRTUALIZATION

40. OFFSCREEN CONTENT

41. BACKGROUND ANIMATIONS

JOS STYLE — MOTION SYSTEM
FASE 14 — EASINGS, CURVAS, RITMO, ACELERACIÓN Y LENGUAJE VISUAL DEL MOVIMIENTO
Esfuerzo recomendado: ULTRACODE
 
⸻
 
MISIÓN
Ahora que la arquitectura del Motion System está construida, accesible y optimizada, toca trabajar en algo extremadamente importante:
cómo se siente el movimiento.
Dos interfaces pueden utilizar:
300ms
y parecer completamente diferentes.
La diferencia está en:
* easing;
* aceleración;
* desaceleración;
* velocidad;
* distancia;
* masa percibida;
* ritmo;
* continuidad;
* relación entre elementos;
* anticipación;
* asentamiento.
Esta fase debe construir un lenguaje cinético propio de Jos Style.
No quiero animaciones genéricas de librería.
Quiero que Jos Style tenga una personalidad de movimiento reconocible.
 
⸻
 
1. AUDITORÍA DE EASINGS
Buscar absolutamente todos los:
* ease
* ease-in
* ease-out
* ease-in-out
* cubic-bezier
* spring
* duration
* delay
* transition
* keyframe timing
existentes.
Crear un mapa.
 
⸻
 
2. ELIMINAR EASINGS ARBITRARIOS
Detectar:
cubic-bezier(...)
repetidos o creados sin criterio.
No eliminar automáticamente.
Determinar primero qué función cumplen.
 
⸻
 
3. MOTION CURVE SYSTEM
Crear una jerarquía semántica.
Por ejemplo:
curve.standard
curve.enter
curve.exit
curve.emphasized
curve.linear
curve.spring
Adaptarla a la arquitectura real.
No copiar literalmente estos nombres si existe una nomenclatura mejor.
 
⸻
 
4. PRINCIPIO DE ENTRADA
Las entradas normalmente deben comunicar:
preparation
→
movement
→
settling
No utilizar necesariamente el mismo easing que para una salida.
 
⸻
 
5. PRINCIPIO DE SALIDA
Una salida normalmente puede ser:
visible
→
accelerate
→
leave
La salida no debería sentirse simplemente como:
opacity → 0
cuando existe una relación espacial clara.
 
⸻
 
6. ENTRADA VS SALIDA
Auditar cada transición importante:
enter
y:
exit
de forma independiente.
Evitar:
enter = exit
por comodidad.
 
⸻
 
7. DISTANCE + DURATION
La duración no puede evaluarse aislada.
Relacionar:
distance
+
duration
+
easing
Una animación que recorre mucha distancia necesita un comportamiento diferente a una microinteracción de pocos píxeles.
 
⸻
 
8. VELOCIDAD PERCEPTUAL
Buscar que elementos equivalentes tengan velocidades visuales similares.
Evitar:
element A → rápido
element B → lentísimo
cuando forman parte del mismo sistema.
 
⸻
 
9. MOTION MASS
Utilizar la percepción de masa de manera coherente.
Conceptualmente:
small element
→ light

large surface
→ heavier

modal
→ substantial

microinteraction
→ immediate
No hacer que un botón parezca pesar lo mismo que un bottom sheet.
 
⸻
 
10. SPRINGS
Auditar todos los springs.
Buscar:
* stiffness;
* damping;
* mass;
* velocity;
* overshoot.
Determinar si cada spring tiene una función clara.
 
⸻
 
11. SPRING TOKENS
Centralizar los perfiles.
Por ejemplo:
spring.snappy
spring.standard
spring.soft
spring.heavy
spring.responsive
Utilizar la nomenclatura que encaje con el sistema existente.
 
⸻
 
12. NO SPRING EVERYWHERE
No convertir cada animación en un spring.
Los springs funcionan especialmente bien para:
* gestos;
* sheets;
* toggles;
* drag;
* elementos físicos.
Pero no necesariamente para:
* fades;
* route crossfades;
* tooltips;
* estados muy rápidos.
 
⸻
 
13. OVERSHOOT
Auditar el overshoot.
Debe ser:
* controlado;
* pequeño;
* intencional.
Evitar que una interfaz premium parezca elástica sin motivo.
 
⸻
 
14. SETTLING
Un elemento que llega a su posición puede necesitar un pequeño asentamiento.
Pero debe ser casi imperceptible.
Evitar:
move
→ bounce
→ bounce
→ bounce
 
⸻
 
15. ANTICIPATION
Analizar si algunas interacciones necesitan anticipación.
Ejemplo:
button
→ tiny press
→ action
No introducir anticipación artificial en todas las interacciones.
 
⸻
 
16. MICROINTERACTION RHYTHM
Las microinteracciones deben ser rápidas.
Ejemplos:
* button press;
* checkbox;
* toggle;
* chip;
* tab;
* icon button.
Deben responder antes de que el usuario tenga tiempo de preguntarse si funcionó.
 
⸻
 
17. TRANSITION RHYTHM
Las transiciones grandes pueden respirar ligeramente más.
Ejemplo conceptual:
micro
→ fast

component
→ medium

page
→ deliberate
Crear una jerarquía coherente.
 
⸻
 
18. MOTION SCALE
Crear si resulta apropiado una escala:
XS
SM
MD
LG
XL
basada no solo en duración sino también en:
* distancia;
* complejidad;
* importancia.
 
⸻
 
19. DURATION TOKENS
Auditar todos los durations.
Eliminar valores casi idénticos sin necesidad:
180ms
190ms
195ms
205ms
si cumplen exactamente la misma función.
Consolidar.
 
⸻
 
20. DELAY TOKENS
Auditar delays.
Un delay debe tener una razón.
Evitar:
delay: 137ms
porque “visualmente quedaba bonito”.
 
⸻
 
21. STAGGER RHYTHM
El stagger debe sentirse:
A
  B
    C
pero no:
A
   B
      C
          D
              E
cuando hay demasiados elementos.
 
⸻
 
22. STAGGER ADAPTATION
En listas pequeñas:
puede existir stagger.
En listas grandes:
reducirlo o eliminarlo.
No hacer esperar al usuario para ver información.
 
⸻
 
23. CONTENT PRIORITY
Los elementos importantes deben aparecer antes.
Ejemplo:
heading
primary action
main content
secondary metadata
decorative content
La motion hierarchy debe respetar la información.
 
⸻
 
24. INFORMATION + MOTION
Nunca utilizar motion para hacer que un elemento importante aparezca demasiado tarde.
El contenido funcional tiene prioridad sobre el espectáculo.
 
⸻
 
25. HERO MOTION
Los elementos principales de una pantalla pueden recibir un tratamiento más elaborado.
Pero debe ser:
* limpio;
* corto;
* controlado.
No convertir cada pantalla en una presentación.
 
⸻
 
26. SECONDARY MOTION
Los elementos secundarios deben utilizar motion más discreto.
Evitar competir con el elemento principal.
 
⸻
 
27. DECORATIVE MOTION
La decoración debe ser la capa menos importante.
Si desaparece:
la interfaz debe seguir funcionando perfectamente.
 
⸻
 
28. DEPTH + EASING
Integrar las curvas con el Depth System.
Ejemplo conceptual:
foreground
→ faster response

background
→ softer response
No todos los elementos deben reaccionar exactamente igual.
 
⸻
 
29. PARALLAX
Si existe:
hacerlo extremadamente sutil.
El parallax debe sugerir profundidad, no convertirse en protagonista.
 
⸻
 
30. BLUR + MOTION
Auditar cómo cambia blur durante:
* modal entrance;
* modal exit;
* navigation;
* sheets;
* overlays.
El blur no debe producir sensación de lentitud.
 
⸻
 
31. OPACITY + MOTION
Evitar depender de opacity para absolutamente todo.
Una transición puramente basada en fade puede hacer que las relaciones espaciales desaparezcan.
Utilizar movimiento espacial cuando realmente comunique contexto.
 
⸻
 
32. SCALE
Auditar scale.
Especialmente:
0.95
0.98
1.02
1.05
Un scale pequeño puede dar sensación de profundidad.
Un scale excesivo puede parecer una animación de marketing.
 
⸻
 
33. MODAL LANGUAGE
Definir el lenguaje específico para:
* modal;
* dialog;
* sheet;
* popover;
* tooltip.
No todos deben entrar igual.
 
⸻
 
34. SHEET LANGUAGE
Un bottom sheet debe sentirse:
* físico;
* conectado al borde;
* manipulable;
* predecible.
Integrar:
velocity
+
spring
+
drag
+
snap
 
⸻
 
35. POPOVER LANGUAGE
Un popover debe ser más ligero.
No utilizar la misma animación de un modal fullscreen.
 
⸻
 
36. TOOLTIP LANGUAGE
Los tooltips deben ser prácticamente instantáneos.
No utilizar:
long entrance
para información pequeña.
 
⸻
 
37. TOAST LANGUAGE
Los toasts deben:
appear
→
communicate
→
leave
sin robar atención excesiva.
 
⸻
 
38. NAVIGATION LANGUAGE
Definir claramente:
root
section
detail
modal
sheet
y asignarles comportamiento.
La profundidad debe poder percibirse.
 
⸻
 
39. BACK NAVIGATION
La vuelta debe sentirse ligeramente diferente de la entrada.
Debe comunicar:
returning
en lugar de:
opening same page backwards
 
⸻
 
40. GESTURE VELOCITY
Las animaciones controladas por gesto deben utilizar la velocidad real del gesto cuando corresponda.
Ejemplo:
slow drag
→
soft settle

fast swipe
→
decisive dismiss
Esto aumenta enormemente la sensación física.
 
⸻
 
41. INTERRUPTION CONTINUITY
Si una animación se interrumpe:
no reiniciar desde el valor inicial.
Continuar desde:
current visual state
 
⸻
 
42. REVERSIBILITY
Cuando sea apropiado:
una animación debe poder invertirse.
Especialmente:
* sheets;
* drawers;
* accordions;
* expandable cards;
* drag interactions.
 
⸻
 
43. VELOCITY-AWARE MOTION
Auditar todas las interacciones donde la velocidad del usuario pueda aportar contexto.
No utilizar siempre una duración fija.
 
⸻
 
44. MOTION TEMPERATURE
Evaluar conceptualmente:
cold
→ precise / restrained

warm
→ soft / expressive
Jos Style debe inclinarse hacia:
preciso + premium + natural.
Evitar motion infantil o excesivamente juguetón salvo donde tenga una función clara.
 
⸻
 
45. BRAND MOTION
Definir qué hace que el movimiento sea reconociblemente:
JOS STYLE
No depender únicamente de:
* color;
* typography;
* shadows.
El motion también debe formar parte de la identidad visual.
 
⸻
 
46. CONSISTENCY AUDIT

open
close
select
delete
save
expand
collapse
navigate
back
y comprobar que sus comportamientos sean consistentes.
 
⸻
 
47. MOTION OUTLIERS
Encontrar las animaciones que:
* son demasiado lentas;
* demasiado rápidas;
* demasiado elásticas;
* demasiado grandes;
* demasiado llamativas;
* utilizan easing diferente sin razón.
Corregirlas.

Preguntarse:

49. AVOID MECHANICAL MOTION
La interfaz no debe sentirse:
linear
robotic
mechanical
cuando la interacción requiere comportamiento natural.
Pero tampoco debe sentirse:
bouncy
cartoonish
random
Buscar el punto intermedio.
 
⸻
 
50. AVOID MARKETING MOTION
Jos Style no debe parecer una landing page animada.
La motion debe estar al servicio de:
* comprensión;
* orientación;
* interacción;
* feedback;
* continuidad.
 
⸻
 
51. MOTION TOKENS DEFINITIVOS
Consolidar:
duration

stagger

Los tokens deben ser la única fuente de verdad.

JOS STYLE — MOTION SYSTEM
FASE 15 — MOTION RESPONSIVE, ORIENTACIÓN, SAFE AREAS Y ADAPTACIÓN MULTIDISPOSITIVO
Esfuerzo recomendado: ULTRACODE
 
⸻
 
MISIÓN
Adaptar todo el Motion System de Jos Style a los diferentes contextos físicos en los que puede ejecutarse.
La aplicación debe mantener una identidad de movimiento consistente en:
* móvil;
* tablet;
* desktop;
* ventanas pequeñas;
* ventanas grandes;
* portrait;
* landscape;
* teclado abierto;
* teclado cerrado;
* dispositivos táctiles;
* dispositivos con mouse;
* dispositivos con trackpad;
* pantallas con diferentes densidades;
* dispositivos con notch;
* Dynamic Island;
* safe areas;
* diferentes refresh rates.
IMPORTANTE:
No queremos simplemente:
mobile = desktop pero más pequeño
Queremos:
el mismo lenguaje de movimiento adaptado al contexto físico.
 
⸻
 
1. AUDITORÍA RESPONSIVE
Antes de implementar:
analiza cómo está estructurado actualmente el responsive.
Identifica:
* breakpoints;
* media queries;
* container queries;
* layouts;
* navegación;
* bottom navigation;
* sidebars;
* modals;
* sheets;
* cards;
* grids;
* headers;
* floating actions;
* safe areas;
* teclado;
* orientation.
No asumir breakpoints.
Utilizar los reales del proyecto.
 
⸻
 
2. MOTION BREAKPOINTS
Determinar si realmente hacen falta variantes de motion según viewport.
No crear breakpoints únicamente por costumbre.
Diferenciar:
layout breakpoint
de:
motion breakpoint
Una animación puede mantenerse idéntica aunque el layout cambie.
 
⸻
 
3. MOBILE MOTION
En móvil:
priorizar:
* respuesta inmediata;
* touch;
* gestures;
* sheets;
* bottom navigation;
* navegación jerárquica;
* safe areas.
Evitar movimientos excesivamente largos porque el espacio físico es menor.
 
⸻
 
4. DESKTOP MOTION
En desktop:
priorizar:
* precisión;
* hover;
* pointer;
* keyboard;
* popovers;
* tooltips;
* side panels;
* ventanas;
* navegación lateral.
No reutilizar automáticamente las mismas transiciones de móvil.
 
⸻
 
5. TABLET
La tablet no debe tratarse automáticamente como:
mobile gigante
ni:
desktop pequeño
Determinar su comportamiento real según layout y input.
 
⸻
 
6. INPUT-AWARE MOTION
Detectar o determinar de forma segura:
touch
mouse
trackpad
keyboard
stylus
y adaptar únicamente lo necesario.
Ejemplo:
touch
→ press / drag

mouse
→ hover / pointer

keyboard
→ focus
 
⸻
 
7. HOVER VS TOUCH
No implementar:
hover-only
para funcionalidades esenciales.
En touch:
utilizar equivalentes apropiados.
 
⸻
 
8. POINTER PRECISION
Un mouse permite interacciones precisas.
Touch no.
Por tanto:
* no exigir precisión extrema;
* no colocar animaciones interactivas demasiado pequeñas;
* no depender de microgestos difíciles.
 
⸻
 
9. TOUCH TARGETS
Auditar todos los controles animados:
* buttons;
* icons;
* close;
* back;
* tabs;
* bottom navigation;
* floating actions.
La animación nunca debe reducir el área real de interacción.
 
⸻
 
10. SAFE AREAS
Auditar:
env(safe-area-inset-top)
env(safe-area-inset-bottom)
env(safe-area-inset-left)
env(safe-area-inset-right)
cuando sea necesario.
Especialmente:
* bottom navigation;
* sheets;
* fullscreen modals;
* floating actions;
* headers;
* dialogs.
 
⸻
 
11. SAFE AREA + MOTION
No animar un elemento hacia una posición que ignora safe areas.
Ejemplo:
sheet
↓
safe-area
El movimiento debe respetar el área segura durante todo el recorrido.
 
⸻
 
12. NOTCH / DYNAMIC ISLAND
Si el entorno lo requiere:
comprobar comportamiento con:
* notch;
* Dynamic Island;
* rounded corners;
* status bar.
Evitar contenido animado bajo zonas críticas sin intención.
 
⸻
 
13. BOTTOM NAVIGATION
En móvil:
auditar:
navigation
+
safe area
+
keyboard
+
gesture area
La bottom navigation no debe:
* saltar;
* quedar debajo del teclado;
* cubrir contenido;
* cambiar de altura bruscamente.
 
⸻
 
14. KEYBOARD OPENING
Cuando aparece el teclado:
la aplicación debe reaccionar de forma estable.
Evitar:
keyboard
→ layout explosion
→ navigation jump
→ content jump
 
⸻
 
15. KEYBOARD RESIZE
Auditar:
visualViewport
si es necesario.
Determinar si el viewport realmente cambia y cómo afecta:
* sheets;
* dialogs;
* forms;
* bottom navigation;
* inputs.
 
⸻
 
16. INPUT FOCUS + KEYBOARD
Al enfocar un input:
el scroll y el teclado deben coordinarse.
Evitar:
focus
→ scroll
→ animation
→ keyboard
→ second scroll
cuando no sea necesario.
 
⸻
 
17. SAFE SHEETS
Los bottom sheets deben adaptarse a:
* safe areas;
* keyboard;
* orientation;
* viewport height.
 
⸻
 
18. FULLSCREEN MODALS
Los modales fullscreen deben funcionar correctamente en:
* portrait;
* landscape;
* móvil pequeño;
* móvil grande;
* tablet.
 
⸻
 
19. ORIENTATION CHANGE
Probar:
portrait
→
landscape
y:
landscape
→
portrait
durante:
* idle;
* navigation;
* modal;
* sheet;
* gesture;
* scroll.
 
⸻
 
20. ORIENTATION DURING ANIMATION
Si cambia orientación mientras una animación está ejecutándose:
no dejar:
* posición incorrecta;
* transform obsoleto;
* elemento fuera de pantalla;
* overlay mal dimensionado.
Recalcular únicamente lo necesario.
 
⸻
 
21. RESPONSIVE SHARED ELEMENTS
Los shared elements deben sobrevivir correctamente a cambios de layout.
Ejemplo:
desktop card
→
detail
versus:
mobile card
→
detail
No asumir las mismas geometrías.
 
⸻
 
22. RESPONSIVE DEPTH
La profundidad puede necesitar adaptación.
En pantallas pequeñas:
reducir efectos visualmente costosos cuando no aporten valor.
No convertir móvil en una versión visualmente inferior.
 
⸻
 
23. RESPONSIVE BLUR
Auditar blur según viewport.
Un blur enorme sobre una pantalla móvil completa puede ser mucho más costoso de lo necesario.
Optimizar área e intensidad cuando sea apropiado.
 
⸻
 
24. RESPONSIVE SHADOWS
Las sombras pueden necesitar ligeros ajustes según contexto.
No crear una colección infinita.
Mantener los mismos tokens semánticos.
 
⸻
 
25. RESPONSIVE DISTANCES
Una distancia de:
24px
puede sentirse distinta en un contexto muy pequeño que en una pantalla grande.
Definir cuándo una distancia debe:
* permanecer;
* escalar;
* adaptarse.
No hacer scaling automático de todo.
 
⸻
 
26. RESPONSIVE DURATION
No modificar durations simplemente porque cambia el viewport.
Cambiar duración únicamente si cambia realmente:
* distancia;
* interacción;
* contexto;
* percepción.
 
⸻
 
27. RESPONSIVE STAGGER
En móvil:
reducir stagger cuando una lista sea larga.
En desktop:
puede tolerarse un poco más cuando la densidad visual sea menor.
Siempre priorizar la rapidez percibida.
 
⸻
 
28. RESPONSIVE NAVIGATION
Auditar:
mobile
→ bottom navigation

desktop
→ sidebar / desktop navigation
si así funciona realmente el producto.
Las dos deben pertenecer al mismo sistema de motion.
 
⸻
 
29. NAVIGATION MORPH
Si una navegación cambia de forma al cambiar breakpoint:
evitar:
bottom nav disappears
sidebar suddenly appears
cuando pueda existir una transición coherente.
Pero no forzar una animación si el cambio de viewport debe ser inmediato.
 
⸻
 
30. RESPONSIVE MODALS
Definir el comportamiento adecuado:
desktop
→ dialog / centered modal

mobile
→ sheet / fullscreen / appropriate modal
según el componente real.
La transición debe adaptarse al nuevo contexto.
 
⸻
 
31. RESPONSIVE POPOVERS
Un popover que funciona perfectamente en desktop puede no funcionar en móvil.
Auditar:
* posicionamiento;
* collision;
* viewport edges;
* touch;
* dismiss;
* animation origin.
 
⸻
 
32. COLLISION-AWARE MOTION
Si un elemento flotante debe cambiar de posición porque no cabe:
no debe teleportarse.
Ejemplo:
preferred position
↓
collision
↓
alternative position
El cambio debe ser estable y, cuando corresponda, animado.
 
⸻
 
33. ANCHOR MOTION
Para:
* popovers;
* tooltips;
* menus;
* contextual actions;
mantener la relación visual con su anchor.
 
⸻
 
34. WINDOW RESIZE
En desktop:
probar:
large
→ medium
→ small
→ large
rápidamente.
No dejar estados visuales obsoletos.
 
⸻
 
35. RESPONSIVE LAYOUT MOTION
Cuando cambia el layout:
los elementos deben reorganizarse sin saltos innecesarios.
Integrar con:
Layout Motion Engine
No crear un segundo sistema.
 
⸻
 
36. GRID CHANGES
Probar:
4 columns
→
3
→
2
→
1
si existe ese patrón.
Evitar que los elementos parezcan desaparecer y reaparecer arbitrariamente.
 
⸻
 
37. TEXT REFLOW
Cuando cambia el ancho:
auditar:
* headings;
* paragraphs;
* buttons;
* cards;
* navigation;
* badges.
El texto no debe provocar movimientos absurdos durante una transición.
 
⸻
 
38. FONT SCALING
Si el usuario aumenta el tamaño de texto:
la interfaz debe seguir siendo funcional.
Motion no debe depender de tamaños fijos que dejen elementos fuera de lugar.
 
⸻
 
39. ZOOM
Probar zoom del navegador cuando sea relevante.
Especialmente:
125%
150%
200%
según el entorno.
No dejar:
* overlays rotos;
* tooltips fuera de viewport;
* botones inaccesibles;
* modals imposibles de cerrar.
 
⸻
 
40. REDUCED MOTION + RESPONSIVE
Comprobar combinaciones:
mobile + reduced
desktop + reduced
tablet + reduced
No asumir que reduced motion solo existe en desktop.
 
⸻
 
41. PERFORMANCE + RESPONSIVE
La variante responsive no debe multiplicar innecesariamente:
* listeners;
* observers;
* animation systems;
* DOM;
* state.
Compartir infraestructura.
 
⸻
 
42. PERFORMANCE + ORIENTATION
Un cambio de orientación puede provocar muchos cálculos.
Evitar cascadas innecesarias de:
resize
→ state
→ render
→ measurement
→ render
 
⸻
 
43. CONTAINER QUERIES
Si el proyecto utiliza container queries:
considerar su impacto en motion.
Una card puede cambiar de layout sin cambiar el viewport global.
 
⸻
 
44. COMPONENT-LEVEL RESPONSIVENESS
Los componentes deberían poder adaptar su motion según su propio contexto cuando sea necesario.
Ejemplo:
small card
→
shorter motion

large card
→
more spatial motion
sin duplicar el componente.
 
⸻
 
45. DEVICE PIXEL RATIO
No diseñar motion basándose únicamente en CSS pixels físicos.
Mantener el sistema independiente del DPR.
 
⸻
 
46. HIGH REFRESH RATE
Probar cuando sea posible:
60 Hz
90 Hz
120 Hz
La animación debe utilizar el tiempo real del frame.
No depender de:
setInterval
para simular movimiento.
 
⸻
 
47. RESPONSIVE GESTURES
Los gestos deben adaptarse a:
* ancho;
* alto;
* dirección;
* edge gestures;
* safe areas.
Evitar thresholds absolutos cuando deban ser relativos.
 
⸻
 
48. EDGE GESTURES
No competir con gestos nativos del sistema.
Especialmente:
* swipe back;
* home gesture;
* notification gestures.
 
⸻
 
49. RESPONSIVE DEBUG MATRIX
Crear una matriz interna de comprobación:
Mobile portrait
Mobile landscape
Tablet portrait
Tablet landscape
Desktop small
Desktop large
Reduced motion
Keyboard open
Keyboard closed
Probar los componentes críticos.
 
⸻
 
50. VISUAL CONSISTENCY
Aunque cambien:
* layout;
* navegación;
* tamaño;
* interacción;
el lenguaje de movimiento debe seguir siendo reconociblemente Jos Style.
 
⸻
 
51. IMPLEMENTACIÓN REAL
No limitarse a documentar.
Implementar las correcciones necesarias en:
* CSS;
* tokens;
* Motion Engine;
* components;
* routing;
* gestures;
* overlays;
* responsive logic.
Si falta una abstracción:
créala.
Si existe una abstracción duplicada:
consolídala.
 
⸻
 
52. NO FORZAR MOTION
Muy importante:
No animar cada cambio de responsive.
Un cambio de orientación o breakpoint puede requerir una actualización inmediata.
La estabilidad tiene prioridad sobre el espectáculo.

el mismo producto adaptándose inteligentemente al dispositivo.
